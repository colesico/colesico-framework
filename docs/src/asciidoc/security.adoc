== What is Colesico-Security

Colesico-Security is a comprehensive security module that provides authentication and authorization capabilities for the framework. It integrates seamlessly with the Service module through code generation, enabling declarative security configuration on service methods.

The module is built around three core concepts:

- **Identity** - represents an authenticated subject with claims, roles, and permissions
- **Authentication** - verifies the identity of a subject using various sources
- **Authorization** - determines if an authenticated subject has permission to perform an action

The module integrates with:

- `colesico-service` - for method-level security via interceptors
- `colesico-config` - for security configuration
- `colesico-ioc` - for dependency injection and scope management

HTTP-specific authentication sources (like `HttpBasic`) are provided by the `colesico-telehttp` module, which depends on `colesico-security`.

== Key features

* Identity management with claims, roles, and permissions
* Pluggable authentication sources
* Configurable authentication strategies (STRICT, IF_NECESSARY, DEFERRED)
* Authorization with granular permission checks
* Security audit interception with declarative annotations
* Task scope integration for request-scoped identities
* Built-in test authentication sources
* Authentication lifecycle handlers
* Impersonation support via `callAs()` and `runAs()`
* Extensible via custom authenticators, authorizers, and authentication sources

== Core concepts

=== Identity

`Identity` is the central abstraction representing an authenticated subject. It encapsulates:

- `id()` - a unique identifier for the subject
- `claims()` - a map of arbitrary attributes associated with the subject

The interface provides convenient methods for role and permission checking: `hasRole()`, `hasPermission()`, `roles()`, `permissions()`. The default implementation `Identity.Default` accepts an ID and a claims map during construction.

Identities are stored in the `IdentityContext`, which is bound to the current `TaskScope`. This ensures that the identity remains available throughout the entire request processing chain.

=== SecurityManager

`SecurityManager` is the central entry point for all security operations:

* `authenticate()` - orchestrates the authentication process using registered sources
* `identity()` - retrieves the current identity from the `IdentityContext`
* `requireIdentity()` - returns the identity or throws `UnauthorizedException`
* `logout()` - logs out the current identity
* `callAs()` / `runAs()` - executes code under a specified identity (impersonation)
* `isAuthenticated()` - checks if an identity exists
* `hasPermission()` - delegates authorization checks to an `Authorizer`

The `SecurityManager` coordinates between authentication sources, authenticators, and lifecycle handlers.

=== Authentication

==== AuthenticationSource

`AuthenticationSource` represents a transport-level participant that extracts authentication requests from the underlying protocol and handles protocol-specific responses.

The `BasicAuthentication` source is provided for testing and development, allowing programmatic credential setting.

==== AuthenticationRequest

`AuthenticationRequest` carries credentials and includes a claims map with `SOURCE_CLAIM` for routing back to the issuing source.

==== Authenticator

`Authenticator` verifies credentials and produces an `AuthenticationResult`. Multiple authenticators can be chained using `@Polyproduce`.

==== AuthenticationResult

The sealed interface with four types:

- `Success` - carries the verified `Identity`
- `Failure` - with error details
- `Continuation` - requires additional challenge
- `Skip` - abstains from decision

==== AuthenticationHandler

`AuthenticationHandler` provides lifecycle hooks for authentication and logout events. Each handler can modify results or abort processing.

==== AuthenticationRegistry

`AuthenticationRegistry` resolves authenticators by request type and retrieves issuing authenticators or sources for existing identities.

=== Authorization

==== Authorizer

`Authorizer` evaluates an `AuthorizationRequest` and returns an `AuthorizationResult`. Built-in authorizers include:

- `IdentityRequiredAuthorizer` - verifies identity presence
- `AffirmativeAuthorizer` - OR logic for plugin systems
- `UnanimousAuthorizer` - AND logic for critical operations

==== SecurityAudit

`SecurityAudit` specifies `AuditInterceptor` classes for method invocation, enabling access control and logging.

==== RequireIdentity

`RequireIdentity` ensures an identity exists before method execution, using `RequireIdentityAudit`.

== Code generation integration

The `SecurityModulator` integrates with the Service module at compile time:

=== Authentication interceptor

When annotated with `@Authentication`, the modulator injects an `AuthenticationInterceptor` field and binds it to the `AUTHENTICATION` phase with configured sources and strategy:

- `STRICT` - always authenticates
- `IF_NECESSARY` - authenticates only if no identity exists
- `DEFERRED` - registers sources in `AuthenticationSourceContext` for later manual authentication

=== Authorization interceptor

When annotated with `@SecurityAudit` or `@RequireIdentity`, the modulator injects auditor fields and binds them to the `AUTHORIZATION` phase.

=== AuthenticationSourceContext

Holds authentication sources bound to the current scope, enabling `DEFERRED` authentication strategy.

== Built-in implementations

=== BasicAuthenticator

Provides login/password authentication with:

- Configurable max authenticated sessions via `BasicAuthConfigPrototype`
- Password hashing (SHA-256 default)
- Account storage abstraction
- In-memory authenticated session cache

=== DefaultBasicAccountStorage

Loads accounts from `accounts.properties` with password hashes and roles.

=== BasicAuthentication source

An `AuthenticationSource` for testing that allows programmatic credential setting via `setCredentials()`.

=== BasicAuthConfigPrototype

Configuration prototype for `maxAuthenticated()`, `passwordDigest()`, and `challenge()`.

== Exception hierarchy

* `SecurityException` - base security exception (extends `ApplicationException`)
* `UnauthenticatedException` - authentication failure
* `UnauthorizedException` - authorization failure

== Maven pom.xml

[source,xml]
----
<dependency>
    <groupId>net.colesico.framework</groupId>
    <artifactId>colesico-security</artifactId>
    <version>${colesico.version}</version>
</dependency>
----

The module is transitive to `colesico-service` and `colesico-config`.
